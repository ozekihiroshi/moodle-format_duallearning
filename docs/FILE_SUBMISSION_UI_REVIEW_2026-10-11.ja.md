## アップロードの停止と比較

毎回、YUIのアップロード用フレームにChromeのブロック表示が出ました。コンソールにはアップロード完了処理で別オリジンのフレームへアクセスしたというSecurityErrorが記録されました。サーバーはアップロードPOSTにHTTP 200を返していました。最初の失敗後の読み取り確認では、33バイトのsubmission-1.txtが学生の下書き領域に存在しました。通常のClose → Filesで一覧へ復帰できました。ブラウザの保護設定やコアコードを変更して応答制限を回避する操作は行っていません。

標準Topicsの課題72でも同じsubmission-1.txtのアップロードで再現しました。Dual Learning固有の問題とは判断できません。ただし、Moodleコアの不具合とも未確定で、Chrome・自動操作接続・検証環境の影響を切り分ける必要があります。最初の拡張機能によるファイル選択拒否は別の問題で、ユーザーによる再接続後に解消しました。その後の操作接続の切断では、新しい検証タブへ移りました。

Topicsはアップロード停止時の選択画面で止めています。同コースの返却・再提出の一巡とTeacher guidedの検証は未実施です。自動操作の影響を切り分けるため、Topicsで手動アップロードしても停止するかユーザーに確認を依頼しました。比較全体が完了したとは扱いません。

## アップロード原因切り分け：デバッグ接続への依存

比較により、検証環境の接続状態への依存が確認できました。ユーザーは、ChatGPTのChromeデバッグ接続中は手動アップロードでも停止すると回答しました。接続をキャンセルし、再読み込み・手動アップロードを行う比較では、正常に一覧へ戻ると回答しました。自動でのファイル選択やクリックのタイミングだけでは説明できず、Dual Learning側に修正を加える根拠はありません。ただし、Chrome・拡張機能・そのリクエスト制御の内部のどこに不具合があるかまでは特定していません。

自動操作の失敗時は、標準Topicsの教師返却欄の未保存下書きにupload-probe.txtをアップロードしました。一時的なApacheの応答ヘッダーログでは、HTTP 200、Content-Type text/plain、Sec-Fetch-Site same-origin、Sec-Fetch-Dest iframeでした。X-Frame-Options、Content-Security-Policy、Locationの応答ヘッダーはありませんでした。lib/classes/output/core_renderer_ajax.phpのファイル送信時の特別処理もtext/plainを指定しており、実際の応答と一致します。それでもブラウザはフレームにブロック画面を表示し、YUIの_uploadCompleteがdocumentを読もうとしてSecurityErrorになりました。Close → Filesではupload-probe.txtが下書きに保存済みと確認できました。

接続中の手動比較でもサーバー応答は同じで、ユーザーは停止を確認しました。切断後の成功はユーザーによる観察結果です。保存したログには成功時と特定できる別のリクエストはないため、成功した対照実験のネットワーク記録まで取得したとは扱いません。

ログには応答状態・クエリを除いたパス・限定したヘッダー・fetch情報だけを記録し、Cookie・認証情報・本文は記録していません。一時的なApache設定は削除し、設定検査に成功してから再読み込みしました。診断ログ設定の反映後に起きたセッション切れは再ログインで対応し、元のアップロード停止とは区別しました。

診断中に採点内容は保存していません。終了後の読み取り検証で、Topicsの公開済み返却は1回目がfeedback-1.txt、2回目がfeedback-2.txtだけと確認しました。診断用ファイルは未保存の下書きにとどまり、学生への返却として公開されていません。製品コード・Moodleコア・公開用ファイル・ブラウザの保護設定は変更していません。

今後のファイルアップロード検証は、デバッグ接続を外して手動で操作し、その後に再接続して確認します。読み込み中だからといってすぐ再送しないことも必要です。下書きへの保存は既に完了している場合があります。接続機構そのものの追加調査は、隔離した最小構成で行う別のツール課題として扱います。Dual Learning側の改修要否を決めるための今回の切り分けは完了しました。
